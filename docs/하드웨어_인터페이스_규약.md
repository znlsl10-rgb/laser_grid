## 0. 한 장 요약

장비가 촬영 한 번에 내보내야 하는 것:

| # | 파일 | 필수 | 내용 |
|---|---|:---:|---|
| 1 | `laser_on.png` | **●** | 레이저 ON 프레임 (무손실) |
| 2 | `camera_params.json` | **●** | 내부 파라미터·기선·격자 사양 |
| 3 | `laser_off.png` | ◐ | 레이저 OFF 프레임 (동일 노출, 연속 촬영) |
| 4 | `imu.json` | ◐ | 조사기 좌표계 중력벡터 또는 자세각 |

● 없으면 검측 불가 · ◐ 없으면 돌아가지만 판정을 **참고값**으로 낮춤

납품 전 자체 확인:

```bash
python3 hardware.py <촬영폴더>              # 한 벌 점검
python3 hardware.py <폴더1> <폴더2> <촬영.zip>   # 여러 벌 한꺼번에
python3 hardware.py --template              # camera_params.json 빈 서식
python3 hardware.py --demo                  # 규약을 만족하는 예제를 만들어 봄
python3 hardware.py                         # 점검기 자체 검증
```

`hardware.py` 는 **혼자 도는 파일 하나**입니다. 저장소를 받을 필요 없이 이
파일만 있으면 되고, 필요한 것은 파이썬과 numpy·Pillow 뿐입니다.

**코랩에서 쓰실 때는 `촬영점검_코랩.ipynb` 를 여세요.** 점검기 소스가 노트북
안에 통째로 들어 있어 인터넷도 저장소도 필요 없고, 셀을 위에서부터 실행하면
됩니다. (없으면 `python3 hardware.py --notebook` 으로 만들 수 있습니다.)

> `.py` 파일을 코랩 **"노트북 열기"** 창에 바로 넣으면
> `Unexpected token '#', "#!/usr/bin"... is not valid JSON` 으로 막힙니다.
> 그 창은 `.ipynb` 만 받습니다. 파일이 잘못된 것이 아니라 넣는 자리가
> 다른 것입니다 — `.py` 는 왼쪽 **파일 탭**에 끌어다 놓고 셀에서
> `import hardware; hardware.colab()` 으로 쓰시면 됩니다.

이 검사기를 통과해야 검측 소프트웨어가 동작합니다. 규약서 문구가 아니라
**이 검사기가 판정 기준**입니다 — 검측 파이프라인은 규약을 만족하는 촬영이
들어온다고 전제하고, `camera_params.json` 이 없으면 아예 받지 않습니다.

### 점검기가 보는 것 — 세 단계

| 단계 | 무엇을 | 못 지키면 |
|---|---|---|
| 1 | 파일이 있는가 | **막힘** — 검측을 못 돌립니다 |
| 2 | 이미지가 쓸 만한가 (형식·노출·선폭·채널) | 경고 — 정확도·판정 등급에 영향 |
| 3 | **사양이 이미지와 맞는가** | **불일치** — 그대로 쓸 수 없습니다 |

3단계가 이 검사기의 핵심입니다. `camera_params.json` 에 적힌 값을 믿지 않고
**이미지에서 직접 재어** 견줍니다.

* **초점거리** — 선 사이 간격은 f 와 발사각만으로 정해지고 거리·기선과
  무관합니다. 그래서 읽은 선 위치를 tan α 에 맞추면 기울기가 곧 f 입니다.
  (예제 촬영: 측정 942.4px / 사양 942.4px, 0.0% 차이)
* **굴림각** — 좌표를 −γ 로 되돌렸을 때 선이 가장 좁은 띠에 모이는 γ 를
  찾아 사양과 대조합니다.
* **선 수·발산각** — 읽힌 선 수가 사양과 맞는지, 발사각 모델(등각/등사인)이
  어느 쪽인지.

선이 몇 개 가려져 있어도 됩니다 — 읽은 선 두 개와 발사각 두 개로 후보를
만들어 가장 많이 맞는 것을 고르므로, 순서가 밀리지 않습니다.

> **기선(baseline_m)은 사진 한 장으로 검증할 수 없습니다.** 깊이 식에
> `Z = −(n·b)/(…)` 로 b 와 Z 가 **b/Z 로만** 들어와서, '기선 2배'와 '거리
> 2배'가 화면에서 완전히 같습니다. 검증하시려면 **거리를 자로 잰 촬영**을
> 한 벌 넣고 `camera_params.json` 에 `"측정거리_m": 1.50` 처럼 적어 주세요.
> 그러면 점검기가 대조해 기선 오류를 잡아냅니다. 이 값이 없으면 점검기는
> "기선을 검증할 수 없다" 고 경고만 남깁니다.

예제 촬영의 격자는 **21×21 선(20×20 칸)** 이고, 기준거리 1.20 m 에서
한 변 1.00 m (칸 50 mm)로 비칩니다. 카메라 화각(66°)을 레이저 부채꼴
(45.24°)보다 넓게 두어 격자가 화면 안에 사각형으로 앉습니다 — 선이 화면
끝까지 이어지면 격자가 어디서 끝나는지 알 수 없습니다.

예제는 광선추적으로 만든 것이라 **정답을 압니다**. 파이프라인에 넣으면
아래가 그대로 나와야 합니다 — 업체 쪽 출력이 이 값에서 벗어나면 규약
어딘가가 어긋난 것입니다.

| 대상 | 참값 | 이 코드의 측정값 |
|---|---|---|
| 벽 (수직도) | 0.0000° / Z 1.500 m | 0.0031° / 1.500 m |
| 바닥 (수평도) | 1.0312° | 1.0123° |
| 동바리1 (축 수직도) | 0.0° / 축 Z 1.270 m | 0.0087° / 앞면 1.245 m |
| 동바리2 (축 수직도) | 1.2° / 축 Z 1.330 m | 1.2939° / 앞면 1.308 m |
| 화소별 깊이 | — | 치우침 +0.06 mm, 산포(MAD) 1.34 mm |

동바리 깊이가 축보다 20 mm 남짓 앞인 것은 오차가 아닙니다 — 레이저가
맺히는 곳은 축이 아니라 **앞면**(반지름 24.3 mm)입니다.

### 굴림 0° 와 20° 는 서로 다른 것을 얻습니다

기본 예제는 굴림 0° 입니다. 격자가 화면에 반듯하게 서고, 연직 동바리에
세로선이 한 줄 걸려 **부재 전 길이를 훑으므로 축 수직도가 가장 잘 잡힙니다**
(측정 0.0087°). 대신 가로선의 레이저 평면이 카메라 광심을 지나 깊이를
전혀 주지 못해(이득 g=∞) **단면(지름·중심)은 측정되지 않습니다**.

굴리면 반대가 됩니다. γ=20° 에서 가로선 이득은 2.9 로 유한해져 가로선
화소가 그대로 삼각측량되고 원형 단면이 가정 없이 측정됩니다. 대신 선이
부재를 가로질러 지나 도막으로만 걸리므로 축 방향은 덜 정밀해집니다.

> **알려진 제약(미해결).** 굴린 구성에서 배경이 가까우면(이 예제: 동바리
> 1.27 m, 벽 1.50 m) 실루엣마다 선 중심이 부재에서 배경으로 미끄러지는
> 점이 몇 개씩 생기고, 그 점들이 둘을 잇는 사다리가 되어 현재
> 세그멘테이션(3D DBSCAN)이 동바리를 벽 평면에 흡수합니다. 점 간격이
> 2 mm 라 밀도로는 끊을 수 없고, 화면상 깊이 불연속을 세그멘테이션 단계에
> 넘겨야 풀립니다. 배경이 충분히 멀면(벽 2.5 m) 굴린 구성에서도 두
> 동바리가 정상적으로 분리·측정됩니다.

### 깊이 구간에는 한계가 있습니다

깊이가 변하면 선이 시차 `f·b/Z` 만큼 움직입니다. 그 움직임이 **이웃 선
간격** 을 넘으면 어느 선인지 구분되지 않습니다.

```
b · (1/Z_near − 1/Z_far)  <  격자 각간격 = FOV / (N−1)
```

이 사양(b=150 mm, 21선, 45.24°)에서는 `Δ(1/Z) < 0.263 m⁻¹` 입니다.
1.2 m 의 동바리를 재는 촬영이라면 배경은 **1.75 m 보다 가까워야** 합니다.
한 화면에 더 넓은 깊이를 담아야 한다면 기선을 줄이거나 선 수를 줄이는
쪽으로 사전 협의가 필요합니다.

## 1. 좌표계 정의

모든 값은 **조사기(레이저 프로젝터) 좌표계** 기준입니다.

```
        Y (아래 +)
        │
        │
        └────── X (오른쪽 +)
       ╱
      Z (전방 +, 피사체 방향)
```

- **원점: 조사기(레이저 프로젝터)의 출사점** — 카메라가 아닙니다
- 카메라는 원점에서 **X축 방향으로만** 기선 `b` 만큼 떨어진 `(b, 0, 0)` 에 있음
- 삼각측량식: `X = b + Z·û`, `Y = Z·v̂`, `Z` = 깊이
  (`û = (u−c_x)/f`, `v̂ = (v−c_y)/f`)
  — 화소 `(u,v)` 의 시선은 카메라 위치 `(b,0,0)` 에서 출발하므로 `X` 에 `b` 가 붙습니다
- 레이저 평면은 모두 원점을 지나므로 `n·P = 0` 입니다(§5). 이 식이 성립하는
  원점이 곧 조사기이며, 원점을 카메라로 잡으면 `n·P` 가 0 이 되지 않습니다
- 화소 좌표 규약: 배열 인덱스 `j` 가 곧 좌표 `j` (화소 중심).
  `j+0.5` 로 보내면 깊이에 계통 오차가 생깁니다
  (실측: 0.5px 어긋남 → 2.5m 벽에서 약 30mm)

기선이 X축이 아닌 방향으로 놓인 구조라면 **사전 협의 필요**합니다.
현재 코드는 X축 기선을 전제로 합니다.

## 2. `camera_params.json`

### 2.1 최소 형식

```json
{
  "camera": {
    "f_px":     1593.0,
    "cx_px":    1224.0,
    "cy_px":    1024.0,
    "sensor_W": 2448,
    "sensor_H": 2048
  },
  "baseline_m": 0.150,
  "grid": {
    "n_vertical":   21,
    "n_horizontal": 21,
    "fov_deg":      60.82
  },
  "laser": {
    "roll_deg":       0.0,
    "tilt_deg":       0.0,
    "wavelength_nm":  520
  }
}
```

### 2.2 값별 규격

| 키 | 단위 | 필수 | 얻는 방법 | 틀렸을 때 영향 |
|---|---|:---:|---|---|
| `camera.f_px` | px | **●** | **체커보드 캘리브레이션** | 1% 오차 → 깊이 1% 오차 (1.7 m 에서 **17 mm**) |
| `camera.cx_px` | px | **●** | 체커보드 캘리브레이션 | 화면 가장자리 깊이가 기울어짐 |
| `camera.cy_px` | px | **●** | 체커보드 캘리브레이션 | 높이 좌표가 어긋남 |
| `camera.sensor_W` | px | **●** | 센서 사양 | 축소본 전송 시 배율이 어긋남 |
| `camera.sensor_H` | px | **●** | 센서 사양 | 〃 |
| `baseline_m` | m | **●** | **조립 후 실측** | 1 mm 오차 → 깊이 **0.7%** 오차 (b=150 mm 기준) |
| `grid.n_vertical` | 개 | ◐ | DOE 데이터시트 | 선 예측이 어긋나 검출률 하락 |
| `grid.n_horizontal` | 개 | ◐ | DOE 데이터시트 | 〃 |
| `grid.fov_deg` | ° | ◐ | DOE 데이터시트 | 〃 |
| `laser.roll_deg` | ° | ◐ | **DOE 장착각 실측** (3절) | 0 이면 가로선이 깊이를 못 줌 |
| `laser.tilt_deg` | ° | ◐ | 조사기·카메라 광축 수렴각 | 선별 평면이 조금씩 어긋남 |
| `laser.wavelength_nm` | nm | ○ | 레이저 사양 | 참고값 (채널은 이미지에서 자동 판별) |

**`f_px`, `cx_px`, `cy_px`, `baseline_m` 은 추정값을 넣으면 안 됩니다.**
이 네 값이 깊이 정확도를 직접 결정합니다. 캘리브레이션 성적서를 함께
주시면 조서 2번 시트에 출처가 `실측(캘리브레이션)` 으로 기록됩니다.

### 2.3 굴림·수렴각을 적는 자리 (세 곳 모두 허용)

파서가 아래 세 자리를 모두 읽습니다. 편한 곳에 적으시면 됩니다.

```json
{"laser": {"roll_deg": 20.0, "tilt_deg": 6.0}}          // 권장
{"grid":  {"laser_roll_deg": 20.0, "laser_tilt_deg": 6.0}}
{"laser_roll_deg": 20.0, "laser_tilt_deg": 6.0}          // 최상위
```

세 자리 모두 없으면 **0° 로 간주**합니다.

### 2.4 선별 평면 법선 (선택 — 있으면 가장 정확)

DOE 선 i 가 만드는 레이저 평면의 법선 `n_i` 를 직접 캘리브레이션했다면
발사각 모델 대신 그 값을 주십시오.

```json
{
  "lines": {
    "V0": {"normal": [-0.9659, 0.0, -0.2588]},
    "V1": {"normal": [-0.9781, 0.0, -0.2079]},
    "H0": {"normal": [0.0, -0.9659, -0.2588]}
  }
}
```

- 선 ID 규약: 세로선 `V0`…`V{n-1}`, 가로선 `H0`…`H{n-1}` (좌→우, 위→아래)
- 벡터는 자동 정규화됩니다 (크기는 임의)
- 평면 방정식: `n·P = 0` (P 는 조사기 좌표계 3D 점)
- 법선을 준 선은 발사각 모델을 건너뛰고 그 값을 그대로 씁니다

**왜 이쪽이 더 좋은가**: 평면 하나에 자유도가 3 이라, 굴림·수렴각·렌즈
왜곡·DOE 개체차가 모두 그 안에 흡수됩니다. 발사각 모델(α_i, β_j)은 이상적
DOE 를 가정하므로 개체차가 그대로 오차로 남습니다.

## 3. 굴림각 `roll_deg` — 이 장비의 가장 중요한 설계 선택

**DOE 를 광축 둘레로 몇 도 돌려서 장착하는가**를 뜻합니다.
`0°` 면 세로선이 화면에서 똑바로 세로, 가로선이 똑바로 가로입니다.

### 왜 중요한가

굴림 `0°` 에서는 가로선의 레이저 평면이 **카메라 광학중심을 지납니다**.
그런 평면은 이미지에서 선 하나로 뭉개져, 그 선 위 어느 점이 얼마나 먼지
알 방법이 원리적으로 없습니다. 실측에서 `|n_x| = 9.2×10⁻⁸`, 깊이이득
`g = 9.6×10⁶` (사실상 무한)이었습니다.

DOE 를 `γ` 만큼 돌리면 `g = 1/sin γ` 로 유한해져 가로선도 삼각측량됩니다.

| γ | 0° | 10° | 20° | 30° | 45° |
|---|---|---|---|---|---|
| 참 원통면 복원 잔차 | **불가** | 0.16 mm | 0.15 mm | 0.13 mm | 0.13 mm |

동바리(Ø48.6 강관) 같은 **원형 부재의 단면**은 가로선만이 보여 줄 수
있습니다. 세로 레이저면이 연직 원기둥을 자르면 기하학적으로 직선이 되기
때문입니다. `γ = 0` 이면 원형 단면을 영원히 측정할 수 없습니다.

### 교환비 — 공짜가 아님

굴리면 점당 깊이잡음이 `1/cos γ` 배가 됩니다.

| 검측 항목 | 굴림의 영향 |
|---|---|
| 수직도·수평도 (각도) | **좋아짐** — 표본이 늘고 면을 격자로 덮어 적합이 안정 |
| 원형 부재 단면 | **가능해짐** (0° 에서는 불가) |
| 평활도 (직선자 처짐) | **나빠짐** — 최대값 통계라 점당 잡음에 민감 |

- 수직도·단면이 주 검측이면 → **γ = 10~45°**
- 평활도가 주 검측이면 → **γ = 0°** 로 두고 세로선 수를 늘릴 것
- `γ = 45°` 에서 세로·가로 이득이 √2 로 같아져 두 계열이 대칭

**결정해서 알려 주시고, `camera_params.json` 에 실측값을 적어 주십시오.**
장착 후 실제 각도가 설계값과 다르면 그 실측값을 적어야 합니다.

## 4. 이미지 규격

| 항목 | 요구 | 지키지 않으면 |
|---|---|---|
| 파일 형식 | **PNG / TIFF (무손실)** | JPEG 압축 잡음이 선 중심을 흔들어 σ_u 증가 |
| 비트 심도 | 8bit 이상 (10~12bit 권장) | — |
| 안티에일리어싱 | **켤 것** | 선 중심이 0.5화소 격자에 갇혀 `σ_u ≥ 1/√12 = 0.289 px` 로 고정 |
| 과포화 | 선 중심 포화 금지 | 능선(ridge)이 평평해져 중심을 못 찾음 |
| 레이저 색 | 무관 (R/G/B 자동 판별) | — |
| 흑백 카메라 | 가능 (밝기 기반으로 전환) | — |

### 깊이 정밀도 계산식

```
σ_Z = σ_u · Z² / (f · b)
```

f = 1593 px, b = 150 mm, σ_u = 0.3 px 기준 → **1.7 m 에서 3.63 mm**

σ_u 는 선검출 정밀도이며 이미지 품질이 결정합니다. 안티에일리어싱 없는
이진 렌더는 0.289 px 가 하한이라, **알고리즘으로는 그 아래로 못 내려갑니다.**

### 레이저 OFF 프레임

권장하는 이유는 배경광 제거입니다. ON−OFF 차영상을 쓰면 햇빛이 드는
현장에서도 선이 살아납니다.

- **동일 노출·동일 게인**으로 촬영
- 두 프레임 간격 **수십 µs** (그 사이 장비가 움직이면 차영상이 어긋남)
- 없으면 채널 과잉분만으로 분리 → 사실상 실내 전용

## 5. `imu.json`

세 형식 중 아무거나 받습니다. 모두 **조사기 좌표계** 기준입니다.

```json
{"gravity": [0.0, 0.829, 0.559]}          // 중력 방향 단위벡터 (권장)
{"accel":   [0.0, -0.829, -0.559]}        // 정지 상태 가속도계 원시값
{"pitch_deg": 34.0, "roll_deg": 0.0}      // 하향각 / 광축 둘레 회전
```

- `gravity`: 크기 무관 (자동 정규화). 장비가 똑바로 서면 `[0, 1, 0]`
- `accel`: 비력이므로 **부호를 뒤집어** 중력으로 씁니다
- `pitch_deg`: 아래로 숙인 각. `roll_deg`: 광축 둘레 회전

### 없으면 어떻게 되는가

장비가 똑바로 서 있다고 가정하고, **모든 판정을 참고값(판정보류)으로
낮춥니다.** 수직도·수평도는 부재 법선과 중력의 사잇각이므로, 장비 자세를
모르면 "부재가 기운 것"과 "장비가 기운 것"을 구분할 수 없습니다.

실측 사례: 바닥 캡처를 IMU 없이 돌렸을 때 `4.4594° 기준초과`가 나왔으나,
자세를 알고 돌리면 `0.0390° 합격`이었습니다. 부재가 아니라 장비가 숙여
있었던 것입니다.

**허용치가 ±0.5° 인 검측에서 IMU 정확도는 ±0.1° 이내를 권장합니다.**

## 6. 촬영 조건 — 검측 대상 기준

| 조건 | 요구 | 이유 |
|---|---|---|
| 부재당 세로선 | **2줄 이상** | 1줄이면 원형 단면이 안 풀려 수직도를 절반만 재고 판정보류 |
| 측정거리 | 사양 피사계심도 안 | 초점이 나가면 선 폭이 퍼져 σ_u 증가 |
| 부재 노출 길이 | 가능한 한 길게 | 짧으면 각도 불확실도가 커져 판정보류 |
| 배경 | 부재 뒤에 면이 있으면 유리 | 가림 그림자로 보조 정보를 얻음 |

**부재당 세로선 2줄 이상**이 실무에서 가장 자주 걸리는 조건입니다.
측정거리 1.2 m 에서 선 간격 24 mm 면 Ø48.6 동바리에 2줄이 걸립니다.
사양(`n_vertical`, `fov_deg`)과 표준 측정거리를 함께 정해 주십시오.

## 7. 파일 이름 규약

이름으로 먼저 가르고, 이름이 없으면 내용으로 판별합니다.

| 종류 | 인식하는 이름 조각 |
|---|---|
| 레이저 ON | `laser_on`, `cast`, `_on`, `on_`, `grid`, `레이저` |
| 레이저 OFF | `laser_off`, `cam`, `scene`, `_off`, `off_`, `배경`, `장면` |
| 카메라 사양 | `.json` 중 `camera`/`f_px`/`baseline_m` 키를 가진 것 |
| IMU | `.json` 중 `gravity`/`accel`/`pitch_deg`/`roll_deg` 키를 가진 것 |

`laser_on.png` / `laser_off.png` / `camera_params.json` / `imu.json` 을
권장합니다.

## 8. 납품 시 함께 주실 것

1. **촬영 샘플 3벌 이상** — 서로 다른 거리·자세로. 위 규약대로 구성
2. **캘리브레이션 성적서** — f, c_x, c_y, 재투영 오차(RMS)
3. **기선 실측값** — 측정 방법과 함께
4. **DOE 장착 굴림각 실측값** — 설계값이 아니라 조립 후 실측
5. `python3 hardware.py <촬영폴더>` **통과 결과 캡처**
